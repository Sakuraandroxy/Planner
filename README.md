# Base Planner

当前完整架构与逐步流程见 [CURRENT_ARCHITECTURE_AND_FLOW.md](docs/CURRENT_ARCHITECTURE_AND_FLOW.md)。

这是一个面向 AirSim 的模块化无人机规划器。本分支注册明确数值动作 `basic_motion`、静态目标接近 `visual_goal_navigation` 和单相机目标上方任务 `visual_goal_above`。旧示例 `navigation` 已删除；`base_planner` 分支不受影响。

`basic_motion` 使用任务解析器提取数值动作，按阶段起点实际位姿换算目标，执行后确认到位及保持，不采图。`visual_goal_navigation` 使用可插拔目标观察能力完成静态目标接近。`visual_goal_above` 使用同一相机临时调整观察角度，定位可见顶部，并组合连续滑窗与关键节点暂停观察。三种任务默认均可被解析和调度，各自管理完成条件。

附近任务的检测协议为包含 `bbox` 和 `surface_points` 的JSON对象；上方任务另有专用协议，增加可见 `top_regions`，每片包含轮廓、孔洞和3至5个屋顶专属支撑点。二者不混用解析器。坐标始终相对当前整张图，原点在左上角，x向右、y向下，归一化到0至1，不相对参考裁剪图。提示词提供输出示例，实际返回仍由对应协议解析。

视觉任务开启滑窗时使用连续速度跟踪：普通航点经过时不停稳，运动中独立采图并在线补点；附近任务进入判定半径、上方任务进入顶部范围并满足高度后暂停并采集停稳证据。队列耗尽允许悬停等待。当前不包含 GroundingDINO、全局地图、完整避障/绕行、持久记忆、动态目标跟随或候选轨迹评分。目标定位、关联及几何完成判断依赖观测质量和人工校准，不能保证所有天气或任意未知环境下成功。

视觉导航的规划 System Prompt 明确要求仅输出一个含5个四维新增航点的完整 JSON 数组；User Prompt 最末尾再次强调格式，并附不带 Markdown 代码围栏的正确输出示例。示例仅说明格式，实际数值仍由模型依据当前任务与观测生成。这是提示词约束，不保证模型每次遵守；实际返回仍由现有解析器检查。请求参数、坐标约定及其他任务提示词保持原样。

视觉导航在输出要求之前集中给出“新增轨迹规划参考”：pending 非空时，使用其预测末端机体系中的目标向量；为空时使用当前观测机体系。目标水平偏角由本地 `atan2(right, forward)` 计算并转换为度，正值向右、负值向左；水平距离接近零时标为未定义。该角度仅描述新增轨迹起点的目标方向，不是强制转角，也不覆盖模型 yaw。提示词说明转角逐点累计，并要求随预测平移和转向更新目标方向；原始“左前方”等文字用于识别任务起点的目标。共享滑窗和飞行执行保持原样，不新增轨迹拒绝规则。

## 当前运行流程

```text
启动CLI → 连接AirSim → 复用server的就绪、按需起飞和位置保持流程（--no-takeoff可跳过起飞）
  → 持续位置保持并等待输入自然语言指令（后续任务复用连接，不重复起飞）
  → TaskParser 解析为 MissionPlan
  → MissionValidator 校验并准备本次使用的Workflow（通过后才执行任务动作）
  → MissionRunner / WorkflowRouter 选择任务工作流
  ├─ basic_motion：读取当前位姿 → 数值动作换算目标 → AirSim直接执行 → API执行结束
  ├─ visual_goal_navigation：停稳观测 → 目标定位/深度几何 → 模型规划 → 协议校验 → 直接执行
  └─ visual_goal_above：找目标/顶部 → 滑窗飞行与暂停换角度交替 → 到达上方 → 完成判断 → 恢复镜头
       ↓ 共用坐标变换、轨迹校验、平滑运动和执行服务
  MotionPlanner → ExecutionService → AirSim Vehicle / MotionTracker
       ↓ 实测反馈与任务专用完成判定
  StageResult → 下一阶段或停止 → MissionResult
```

每个航点的平移量和偏航量，都相对于前一个预测航点表示。AirSim 执行时将位置与偏航结合控制，因此无人机的移动方向可以与机头/相机朝向不同。相机适配器会读取图像返回的相机位姿，并获取相机 FOV；不会假设相机一定水平朝前。

`basic_motion` 等待原生运动结果、实际位置/朝向到达及定点保持后才返回 `completed`，完成依据为 `local_measurement`。`visual_goal_navigation` 首次定位后保存本阶段目标状态，只有通过绑定点半径、停稳观测确认和独立模型完成判定，才返回 `reached`；其依据是位置估计结合当前图像评估，不是仿真器目标位置真值。

## 配置和启动

未实现的进度复核接口及 `progress_review` 配置已删除；旧自定义配置需要移除该配置节。目标完成判断继续使用现有独立模块，各任务保留自己的结束逻辑。

先检查并按本机环境修改 `config/base.yaml`，再安装依赖：

任务解析、目标检测、完成判断默认分别配置为DeepSeek官方 `https://api.deepseek.com`、`deepseek-flash`（V4.1 Flash）。
三个角色各自独立保留URL、model、api_key、api_key_env和request_format，不合并配置，轨迹规划仍使用原Qwen后端。
运行前分别设置 `TASK_PARSER_API_KEY`、`TARGET_DETECTION_API_KEY`、`TASK_COMPLETION_API_KEY` 为官方密钥；可填同一个实际key，但读取项相互独立。
旧中转密钥未带入官方配置，原配置已完整备份到Git忽略的 `.local-config-archive/`，不参与运行。
主配置的 `request_format: deepseek` 使用官方请求字段：`max_tokens` 与 `thinking`。
本地以 `max_completion_tokens` 配置生成预算，解析、目标检测和完成判断当前均为2048，均使用`reasoning_effort: none`关闭思考，DeepSeek请求发送`thinking: {type: disabled}`；轨迹规划也配置为`thinking: disabled`。角色配置彼此独立。
选择 `request_format: openai` 可保留原 `max_completion_tokens` / `reasoning_effort` 格式；旧解析构造参数不带这些设置时仍使用原max_tokens/temperature格式。
协议选择由配置显式注入，不按URL或模型名猜测，不静默改参数重试；提示词、mission_plan_v1、检测框和布尔完成协议保持。
官方说明：[模型与端点](https://api-docs.deepseek.com/quick_start)、[请求字段与思考开关](https://api-docs.deepseek.com/api/create-chat-completion/)。

```bash
pip install -r requirements.txt
```

交互式启动：

```bash
python run_airsim_cli.py
```

直接执行单条指令：

```bash
python run_airsim_cli.py --instruction "上升12米"
```

连接 AirSim 但不自动起飞：

```bash
python run_airsim_cli.py --no-takeoff
```

CLI 与 server 使用相同的起飞和位置保持实现：已经在空中时跳过起飞；原生起飞未确认但实测已上升时，
继续确认位置保持。终端等待输入时仍在控制线程持续保持位置，每条任务结束后重新确认保持。
`--no-takeoff` 不会从地面自动起飞；在空中使用时会保持当前位置。CLI 不启动 HTTP 服务或自动重连。

附近任务和上方任务共用正式暂停取图：等待现有低速、低转速条件后采集，拍摄期间持续保持位置。
如果拍摄期间发生短暂漂移，本帧不用于完成判断，系统在同一个观测截止时间内继续保持并重新采集；
不会因此立即清空轨迹或判任务失败。`Stopped image deferred` 日志会记录保持参考、图像位姿和实测状态。
移动中的规划取图不等待停稳；基础动作、空闲保持继续使用原有的到位条件。

通过 Camera API 连续保存相机实际画面（包括配置了 pitch/yaw/roll 的相机）：

```bash
python run_airsim_cli.py --record-camera-api --camera-record-mode frames
```

录制图像、深度和元数据默认保存到 `output/camera_api/<时间戳>/` 下。录制器使用独立的 AirSim RPC 连接，避免主连接等待飞行指令时停止采集。

### 唯一主配置与模型切换

所有运行参数统一维护在 `config/base.yaml`；各任务的完成判定规则放在 `config/tasks/`。

### 飞到目标上方

新增任务类型 `visual_goal_above`，可直接输入“飞到前方建筑上方5米”或“飞到红车上方”。
米数表示高出目标顶部的距离；明确指定时按该高度及容差完成，未指定时默认至少5米，允许更高观察。任务参数位于
`config/tasks/visual_goal_above.yaml`，模型角色继续使用主配置中独立的检测、规划和完成判断配置。

该任务使用同一台相机。首轮检测只定位目标，返回框和表面点，`top_regions`固定为空；
本地也忽略首轮模型意外返回的顶部，避免过早建立错误屋顶目的地。
之后用已绑定目标框的上沿和图像拍摄时的相机姿态比较世界水平线，
不把图像中线当水平线，也不从零散表面点推断建筑顶部高度。
当框顶未被画面截断、上沿低于世界水平线时，开始请求同一目标的顶部。
这是顶部观察机会，不表示已经到达上方。已有屋顶后使用实测顶部高度判断是否仍处于其上方。
所有主动位移，包括升高以获得顶部视角，均由规划模型输出五点轨迹；不插入固定步长上升。
寻找屋顶和接近上方都连续使用滑窗，按现有规划间隔补点，不再固定每5秒停车或每批清空轨迹。
首次获得屋顶、需要调整相机、恢复丢失目标或进行完成判断时才主动暂停。
提示词提供当前观察阶段及仰角所属帧和位姿。
需要换视角时才暂停，向已绑定建筑上部斜视；符合上方到达条件后才竖直下视完成观察。
相机改变后看丢目标会恢复最近一次看见目标时的镜头姿态，必要时重新朝向已绑定位置。
框只指导观察，不作为屋顶范围或高度。旧的固定角度轮换和本地上升步长配置已删除。
飞行时沿用现有滑窗和5秒规划间隔，视角变化不改变航点坐标约定。
本地每1秒采图，普通目标检测间隔5秒；队列满时仍继续采图，采图不代表调用模型。
顶部由每个区域的3～5个屋顶支撑点读取米制深度、拟合局部平面，再将轮廓射线投影到该平面。
保存有限多边形、孔洞、平面及支撑点，不生成密集三角网格；平面只在轮廓内定义屋顶高度。
轮廓在水平线处无法完整投影时，保留可计算的支撑点局部区域，不凭空补齐远处边界。
首次目标参考图和世界定位点保留阶段身份；同一次检测请求据此识别同一目标，不保留首次屋顶作为永久身份锚点。
后续检测必须与绑定参考点、上一轮已接受表面点或已确认屋顶的投影相符，才更新当前框和几何。
不要求所有点都在框内；投影只能辅助参考图识别，并不独立证明身份。
明显冲突或绑定点不在视野时保留原目标与屋顶，暂停并朝原位置重新观察，不把别的建筑绑定进来。
当前有效屋顶观测及上一份相关观测作为阶段内几何参考，不逐帧累积或做历史网格融合。
新观测优先；目的地暂时在视野外时保留它，明确纠正旧范围时重新选择同一目标上的位置。
不新增面积、倾角或邻域支持比例门槛。
目标裁切或需转换顶部观察视角时允许暂停；10秒是普通换视角冷却时间，目标关联失败立即恢复观察。
所有主动暂停观察后都清空旧队列，从实测位姿重新规划。
首次得到屋顶或原目的地失效时也可清空旧队列；普通屋顶补充直接提供给下一轮规划，不反复停稳。
检测图标注已绑定目标的预测位置，提示词区分初始选定方向和当前方向；预测标记不作为实测表面点。
规划提示附从pending末端计算的五点几何续接参考，供模型减少坐标和累计转角错误，不替换或审核模型轨迹。
没有“接近点的暂停半径”；机体水平坐标进入顶部表面范围并满足高度后，才暂停完成观察。
相机固定朝世界竖直向下，用这张新图更新顶部后再次计算包含关系和净高，再由独立模型结合图像判断。
计算会考虑相机安装偏移，模型输入图标注机体正下方位置；完成判断仍只返回true或false。
false会清空过时队列继续规划；完成、停止和失败时恢复阶段开始前的相机安装姿态。
阶段预算和规划次数不会因清空队列重置。检测异常继续沿用可用信息；诊断写入不决定任务成败。
上方任务检测协议新增`top_regions[].support_points`；附近任务协议、轨迹5点4维格式及HTTP API不变。
旧的网格拟合容差和固定执行时间段配置已删除。本地日志区分几何处理、待完成请求和保持等待耗时。
完成观察图、机体投影叠图、深度和几何测量保存在同一次任务诊断目录。
上方任务的诊断文件在独立写入线程保存，阶段结束后排空已有写入任务，不阻塞飞行控制。
共享AirSim速度跟踪异步续发指令，`airsim.velocity_command_duration_s`默认0.2秒，
与控制更新周期分开；正常续发替换旧指令不算执行失败，RPC错误仍向控制线程报告。
上方规划提示词明确写出`-dz`上升、`+dz`下降；相机角度不改变运动坐标。
每轮新增轨迹参考单独说明观测位姿与pending预测队尾，表面点只辅助观察，屋顶上方目的地单独列出。
寻找顶部时观察方向使用保留的初始建筑参考，最新已接受表面点仍供模型理解场景；
水平转向参考考虑相机朝向偏移，明确允许竖直上升，不能因最初的“左前方”一直左转。
速度和规划间隔仅提供短轨迹尺度参考，不增加固定步长、固定爬升或输出后的方向修正。
AirSim适配器对每个RPC客户端的事件循环作局部适配，处理旧msgpack的超时回调重入及Tornado中断后的运行状态；
不修改SDK安装包、不新增控制线程，也不等待每条速度指令持续结束。
原始阶段错误和后续清理错误分别记录；HTTP接口及输入输出字段保持不变。

### 主要目录细分

- `run_airsim_cli.py` 负责命令行参数、连接与关闭、用户输入和结果展示。任务决策、模型请求和 AirSim 业务逻辑不应堆进 CLI。
- `config/schema.py` 定义有类型的配置结构；`config/loader.py` 负责读取并校验 YAML。环境路径、凭据等本机参数应留在本地配置中。
- `planner/domain/` 存放 `MissionPlan`、`Observation`、`WorldPose`、轨迹、进度状态和结果等核心数据。领域对象不应直接调用 API 或读取 YAML。
- `planner/ports/` 声明调用方需要的接口，例如 `TaskParser`、`ObservationSource`、`TrajectoryPlanner` 和 `Vehicle`。接口描述“要做什么”，具体方式由适配器实现。
- `planner/application/` 校验解析结果、按顺序运行阶段，并通过 `TaskKind` 路由到工作流；不负责图像处理或 AirSim 细节。
- `planner/workflows/` 按任务建立子目录，编排该任务的观测、规划、执行、复核和退出流程。公共接口和延迟组装包装留在外层，任务目录通过 `__init__.py` 导出入口类。
- 各工作流管理自己的结束逻辑；具体任务的搜索及退出策略放在各自任务目录的 `termination.py` 中，不要求实现统一的公共退出接口。
- `planner/capabilities/` 放置多个工作流可以共享的任务能力，当前实现静态目标关联、深度估计和 near 完成条件；尚无持久记忆系统。
- `planner/capabilities/basic_motion_conversion.py` 将数值动作换算为世界目标；`ports/basic_motion_vehicle.py` 定义直接执行接口，AirSim适配器实现原生运动API调用。基础动作没有净空、轨迹审核或到位复核模块。
- `planner/capabilities/targeting/` 实现目标关联及 RGB 射线到深度的几何映射；`completion/` 实现 near 到达条件。这里不发送模型 HTTP 请求。
- `planner/adapters/target_detection/` 实现独立角点检测后端；本地定位和关联在 `capabilities/targeting/`，不需要启动 GroundingDINO。
- `planner/workflows/visual_goal_navigation/workflow.py` 编排导航任务；同目录 `continuous.py` 负责连续模式，`approach.py` 和 `flight.py` 协调分段流程及完成判断调用，`session.py` 保存阶段局部状态，`termination.py` 管理搜索、预算及退出策略。
- 视觉工作流直接执行有效Qwen轨迹；`planner/adapters/diagnostics/visual_goal_trace.py` 实现 TaskTrace 接口，保存诊断证据。安全检查是单前视深度支持的采样检查，不是全向避障保证。
- `planner/visual_goal_bootstrap.py` 只装配新任务依赖，由共同 bootstrap 显式调用，不处理任务运行循环。
- `planner/services/` 放置跨适配器复用的流程和转换逻辑；运动段生成及运动曲线位于 `services/motion/`。
- `planner/adapters/airsim/` 封装 AirSim RPC、车辆控制、相机观测、平滑运动跟踪和录制等仿真器相关实现。
- `planner/adapters/task_parser/` 实现任务解析模型协议；`planner/adapters/trajectory_planner/` 实现轨迹规划模型协议。对应提示词和响应解析应留在各自功能边界内。
- `planner/adapters/trajectory_planner/prompts/` 管理规划任务提示词构造。提示词策略与网络传输、响应解析分开，便于不同任务选择不同 prompt。
- `planner/extensions/` 当前只是显式白名单注册骨架，不是自动扫描或动态加载机制。禁止根据模型输出导入或执行任意模块。
- `planner/bootstrap.py` 是组合根：创建具体适配器，通过接口注入依赖，并注册 `TaskKind → Workflow` 映射。
- `tests/` 按测试边界组织。普通自动化测试优先使用 `fakes/`，不依赖 API key、在线模型服务或正在运行的 AirSim；需要仿真器的测试应明确标出前置条件。
- `output/` 仅用于本机运行产物，不放源码或共享配置模板。

## 如何添加一种新任务

例如后续增加巡检、独立搜索或道路跟随时，按显式链路扩展：

1. 在 `planner/domain/` 中增加 `TaskKind` 成员和专属的不可变参数类型，并扩展 `MissionStage` 的参数类型，避免用无约束的通用字典承载所有任务参数。
2. 更新任务解析提示词、响应解析/工厂和 `MissionValidator`。对未知任务类型、缺失参数和错误参数明确拒绝。
3. 在 `planner/workflows/<任务名>/workflow.py` 实现独立工作流，由该目录的 `__init__.py` 导出入口类；按实际职责增加内部文件。为循环设置配置化或明确的上限，并返回可解释的完成、停止和失败结果。
4. 只为该任务接入需要的能力。可复用的任务逻辑放在 `capabilities/`；需要替换实现的外部依赖先在 `ports/` 定义窄接口，再放入合适的 `adapters/` 实现。
5. 在 `planner/bootstrap.py` 装配该工作流，并注册 `TaskKind → Workflow`。由 `WorkflowRouter` 做路由，不要把任务判断分支堆入 `MissionRunner`。
6. 补充输入合法性、错误处理、路由、成功/失败传递及与其他阶段交互的单元、契约和集成测试。

不同任务可以使用不同的提示词与退出策略：提示词放在对应 adapter 的 `prompts/` 中，由任务工作流/规划器选择；任务专属退出策略放在 `workflows/<任务名>/termination.py`，结束和退出逻辑由各工作流自行组织。不再保留未接入执行路径的公共退出接口。

## 如何添加新模块或外部集成

先判断模块的职责，再决定落点：

- 任务步骤编排：`planner/workflows/`
- 多任务共用的任务能力：`planner/capabilities/`
- 共享的数据转换或执行协调：`planner/services/`
- 模型、仿真器、硬件或网络服务实现：`planner/adapters/`
- 核心数据类型：`planner/domain/`
- 可替换依赖的接口：`planner/ports/`

如果需要更换实现，在 `ports/` 定义足够小且有类型的接口，并通过构造函数注入实现。不要要求所有模块继承一个万能父类：只有确实需要可替换性时才定义 `Protocol`，具体实现使用普通类即可。新增配置时更新 `config/schema.py` 和 `config/loader.py`，再在 `planner/bootstrap.py` 装配。不要使用隐藏的全局注册、导入时副作用或模型控制的动态导入。对于会访问外部服务或仿真器的模块，记录输入输出、异常、超时、状态生命周期和资源所有权。

## 如何适配一种新仿真器

例如增加其他仿真器时，仿真器 SDK、RPC 和坐标系差异都应封装在对应的适配器目录中；工作流和领域层不应直接导入仿真器 SDK。

1. 在 `planner/adapters/<仿真器名>/` 新建适配器包，分别实现 `Vehicle` 和 `ObservationSource`：前者提供当前位置/姿态、执行运动段、取消、悬停及碰撞状态；后者采集并返回统一的 `Observation`。仿真器特有的连接、传感器和运动控制辅助类也放在此包内。
2. 在适配器边界把仿真器数据转换为项目统一的领域语义。`WorldPose`、`MotionSegment`、相机位姿、内参、RGB 和以米为单位的深度都必须语义一致；尤其要核对世界坐标方向、单位、yaw 正方向、角度单位、机体/相机坐标变换及深度定义。若仿真器采用不同坐标系，应在适配器中显式转换并增加正反向转换测试，不要把坐标系特例散落到 workflow 或 prompt。
3. 核对 `Vehicle.execute_segment()` 对 `MotionSegment` 的执行语义：从起点到终点、平移和 yaw 同步、速度/时长限制、悬停与取消行为，以及运行中碰撞检查。仿真器 API 不同可以使用不同控制实现，但要满足同一个 `Vehicle` 契约；低层跟踪器放在该仿真器自己的适配器包中。
4. 处理仿真器生命周期。当前 `run_airsim_cli.py` 直接通过 `Runtime.connection` 调用 AirSim 的 `connect()`、`prepare_vehicle()`、`takeoff()` 和 `shutdown()`；`bootstrap.py` 也直接创建 `AirSimConnection`。所以新增仿真器时，不能只替换 `Vehicle`：应先在 `planner/ports/` 定义通用的会话/生命周期接口（例如 `connect()`、`prepare_vehicle()`、`takeoff()`、`shutdown()`），由各仿真器适配器分别实现；再在 `bootstrap.py` 选择并装配对应组件，让 CLI 依赖该接口而非 AirSim 专属方法。不要把生命周期控制代码复制成多个 CLI 分支。
5. 在 `config/schema.py`、`config/loader.py` 和 YAML 配置中加入必要的仿真器选择与连接、相机、速度、超时等参数。若需要在同一代码版本中选择多种仿真器，应显式配置仿真器类型并在 bootstrap 中白名单分派；避免散落的字符串判断和隐式自动发现。凭据和机器专属地址继续留在本地配置。
6. 检查通用逻辑是否真的与仿真器无关。可复用的 `ExecutionService`、轨迹变换、校验、运动规划和 `ObservationGate` 应继续依赖 `Vehicle` 等接口；如果它们出现具体 SDK 类型或仿真器方法名，应将相关细节移回适配器，或先定义必要的窄接口。
7. 为新适配器增加契约测试：统一的姿态/坐标转换、观测字段和 RGB-深度配对、执行运动段、纯 yaw 旋转、取消/悬停、碰撞上报、连接失败和关闭清理。用 fake 仿真器客户端测试常规路径；需要真实仿真器的测试单独标记并说明启动条件。

完成后，至少确认原有 AirSim 路径仍可运行，并运行 `python -m pytest -q`。如果生命周期接口或领域坐标语义需要调整，应先同步更新对应 Port、CLI/bootstrap 和契约测试，再接入新仿真器；不要让某个仿真器的特殊假设悄悄改变所有现有任务的行为。

## 从入口到 AirSim 的调用关系

```text
CLI
 → PlannerApplication
 → TaskParser
 → MissionValidator
 → MissionRunner
 → WorkflowRouter
 → 对应任务 Workflow
 → 观测 / 轨迹规划 / 校验与坐标变换
 → MotionPlanner
 → ExecutionService
 → AirSim Vehicle 适配器
 → AirSim
```

任务工作流负责任务层的观测、重规划和退出决策；运动跟踪器负责单个运动段中的低层反馈控制。轨迹 API 正常返回或飞完轨迹，不等于已经证明语义任务完成。

## 基础数值动作：basic_motion

本分支使用独立的 `BasicMotionWorkflow`，不再保留示例 `navigation` 工作流。任务解析模型将明确的数值命令转换为动作参数，基础动作流程**不请求轨迹规划模型、目标定位模型或完成判断模型**，经坐标换算后直接执行，共用飞行控制权的协调机制。

例如“上升12米”的解析结果为：

```json
{
  "protocol_version": "mission_plan_v1",
  "stages": [{
    "stage_id": "stage_1",
    "kind": "basic_motion",
    "parameters": {
      "instruction": "上升12米",
      "forward_m": 0,
      "right_m": 0,
      "up_m": 12,
      "yaw_right_deg": 0
    }
  }]
}
```

参数为相对**该阶段起始实际姿态**的动作：`forward_m` 正向前、负向后；`right_m` 正向右、负向左；`up_m` 正上升、负下降；`yaw_right_deg` 正右转、负左转。转换为运动协议时，上升12米对应 `[0,0,-12,0]`，NED 的正 Z 向下约定不变。

- “左转90度，然后前进5米”拆为两个阶段；第二阶段以前一阶段执行后的实际朝向为基准。
- “向前8米、向右5米，同时右转15度”是一个同步动作阶段。
- 支持有符号偏航动作及完整多圈转动；基础动作不套用视觉轨迹的步长和180°转角上限。视觉轨迹的四维数组及其协议保持原样。
- 不猜测缺失距离/角度，不支持绝对高度或世界坐标命令。道路跟随、绕行、穿越、动态目标等未实现任务明确拒绝；若长任务含不支持部分，解析器应拒绝整条任务，不执行一个省略了剩余动作的计划。

### 直接执行及配置迁移

基础动作仅要求任务解析提供完整、有限的数值参数；不进行净空确认、空间边界、动作距离/角度上限、轨迹审核、起点漂移、碰撞等执行前检查。执行后会核实实际位置和朝向。旧 `basic_motion:` 配置块及对应的净空/碰撞配置已删除；外部旧配置需移除此块，未知配置仍按通用加载规则报告错误。

单纯平移先用 `moveToPositionAsync` 飞到终点前的交接位置，再由定点保持服务完成剩余移动和减速；交接距离按现有速度、加速度及jerk计算，短距离直接使用定点保持。单纯转向调用 `rotateByYawRateAsync`；同步平移与转向使用世界坐标速度及有符号偏航速率的 `moveByVelocityAsync`，时长由距离、速度及转角计算。原生动作结束后由共享定点保持服务闭环补偿至请求的世界位置和朝向，并等待观测时间窗成立。平移的原生返回False或None时记录返回值，继续按原请求的固定世界目标保持并实测确认，不重复相对动作；转向仍保留原生执行结果判断。速度使用 `airsim.speed_mps`，转动时间参考 `motion.max_yaw_rate_deg_s`；它们用于执行换算，不限制任务总距离或总转角。

请求位置和朝向实测到达并保持后，结果才标为 `local_measurement`；最终位姿不可读或未到位均不报告成功。API异常或用户中断时取消/悬停，不自动重复相对动作。原有共享飞行控制权协调保持，防止与未结束的旧请求并发抢占。

默认CLI启动后先连接、获取控制权、解锁、起飞并悬停，再接受任务；后续基础动作相对各阶段起点计算，例如起飞后“升高10米”使当前NED z减10。已在空中可用 `--no-takeoff`。基础动作不需要独立配置块；真实API及AirSim效果仍需实验验证。

## 低空平视视觉目标导航：当前实现

本任务显式调用目标检测模型，返回对象`{"bbox":[[x1,y1],[x2,y2]],"surface_points":[[x,y],...]}`。坐标相对完整当前RGB图像归一化，左上角为原点，x向右、y向下。模型自主选择0～5个当前可见表面点，不要求凑满、对称或包含中心；目标不可辨认时返回`{"bbox":[],"surface_points":[]}`。旧纯bbox列表不再接受。
本地对每个模型点按RGB/深度各自内参映射，直接读取原始深度并反投影；跳过没有有效深度的点，以三维距离无人机最近的有效采样点作为原始采样代表；绑定后保留全部有效点，导航距离取最近点的水平距离。诊断图标注全部点，事件记录各点深度结果和被选中的世界点；多个点不等于完整目标边界。空点集或全部深度无效时不生成框中心替代点，沿用现有未获得有效定位的处理。当前没有沿途记忆检测或跨阶段表面拼接。
原始定位深度只检查有限、为正且不低于`depth.min_m`（当前0.5米），不受`depth.max_m`（当前200米）显示上限限制；201米、350米等数值按原值参与世界坐标计算，不截断。`depth.max_m`仅用于显示；当前`log_inverse_gray_v1`把超范围深度显示为黑色，原始深度数组不变。完成半径与显示上限独立，不新增替代测距上限或邻域检查。
公共规划System Prompt第18条改为以User Prompt中的实际显示协议解释亮度、截断和黑色含义，并说明显示范围不限制所提供的米制目标坐标。消息结构、图像编码和五航点协议不变；训练数据及训练侧共用System文件本次未同步修改，不能据此声称训练提示词已更新。
首次按任务描述找到目标并得到有效表面点深度后，立即锁定全部有效表面点及参考图。
后续候选逐一匹配首次表面点，只允许在对应首次点0.5米范围内更新；新位置不会扩张初始点集。远处错车、空框、无效采样深度或检测请求失败不覆盖绑定位置，继续按原绑定点导航。
仅未绑定时进行有限原地搜索；绑定后不自动重选目标。不使用邻域比例、点云或路径包络审核。

Qwen每次返回5个NEW四维点，基本协议/数值和锚点有效性校验通过后，整批依序执行。
不再执行场景空间审核、6m/8s批准前缀或转角裁剪。速度/加速度/yaw控制、到位、停止和总预算保持。
滑窗预取不改变控制权；规划次数用完只停止申请新点，已有点继续执行。

`sliding_window.enabled: true` 时由 `ContinuousExecution` 连续跟踪队列，普通航点不发送停稳指令。
连续跟踪通过`motion.continuous`配置前瞻距离与平移/偏航jerk。速度预算查看整个授权队列，提前协调短航段的转向时间、转弯及队尾停车；中间点和批次切换延续速度与加速度状态。模型有符号yaw仍逐点核实，原地旋转保持位置，零位移零yaw点不额外产生停留。普通航点不必停稳，短段大转角和急弯会提前降速；前瞻参数只影响连续跟踪；平移/偏航jerk参数也用于共用定点保持。
飞行期间约10Hz采样控制诊断到有界内存缓冲，阶段退出并处理停止请求后保存为实验目录下的`control_samples.csv`，包含控制周期、指令/实测速度、指令加速度、yaw误差及AirSim实测俯仰/横滚。该CSV用于分析点头，不代表姿态已验证平稳。具体算法与验收边界见[连续运动跟踪](docs/CONTINUOUS_TRACKING_2026-10-16.md)。
`planning_interval_s: 5.0` 以实际提交时间为基准；首次立即请求，正常请求至少间隔5秒。
最多一个Qwen请求在途，pending最多5点、本地缓冲最多10点；队列大于5点时延后提交，
队列耗尽时允许提前补点，并受失败退避、请求次数和阶段预算约束。5秒不保证恰好剩3点。
只读连接在运动中采图，通过图像相机位姿和人工配置的安装外参恢复图像时刻机体位姿，
按AirSim时间戳对齐pending与实测历史；不把旧预测平移到新位置。

目标检测独立按5秒最小间隔刷新。Qwen收到目标相对图像时刻无人机及预测pending末端的两组
`[前,右,下]` 坐标，以及来源和年龄；不再接收目标bbox或目标世界坐标。
当前无人机世界位姿、相机几何、原始双语指令和执行上下文仍保留。

## HTTP后端

在运行planner的Python环境中安装依赖，然后启动服务：

```bash
python -m pip install -r requirements.txt
python server.py
```

默认监听`0.0.0.0:8080`，也可以用`python server.py --host 127.0.0.1 --port 8080`覆盖地址和端口。
模型及相机仍使用`config/base.yaml`，`--config`可以指定其他完整配置；四种模型密钥继续分别配置。
新增`server`配置块设置监听、浏览器跨域来源、心跳、重试间隔和日志缓冲条数。不要同时启动CLI和server控制同一架无人机。

服务启动后先返回`connecting`，后台连接AirSim并准备无人机。在地面时起飞，已在空中时悬停；准备好后返回`idle`。
新地图准备期间，默认等待无人机状态时间戳持续推进并稳定2秒，再确认API控制权和解锁结果；起飞后确认已离地并停稳，才进入`idle`。`server.readiness_stable_s`和`server.readiness_poll_interval_s`分别设置稳定期和采样间隔；旧配置省略时采用默认值。
HTTP使用一个worker，不启用热重载。唯一的planner执行进程在自己的主线程里创建和使用原有Runtime。

| 接口 | 用法 |
|---|---|
| `POST /api/tasks` | JSON为`{"instruction":"飞到右前方第一辆红色汽车附近"}`；空闲时返回202、任务编号及`running` |
| `GET /api/status` | 例如返回`{"state":"idle"}`；状态有`connecting`、`idle`、`running`、`stopping`，空闲不是上一任务成功的证明 |
| `GET /api/logs?cursor=0` | 返回日志列表和`next_cursor`，下次传回游标；模型原始返回、阶段结果及错误会出现在这里 |
| `POST /api/stop` | 中断任务，先退出旧执行进程，再取消AirSim旧运动并悬停；准备好后可提交新任务 |

运行中或清理中提交新任务返回409，连接准备中返回503；第一版不排队、不提供任务数据库、单任务查询或关闭服务API。
停止任务会重新建立内部RPC客户端，不重新起飞。旧任务的后续阶段、目标参考图、滑窗队列和在途结果全部丢弃。
停止接管先记录当前NED参考位置，使用零偏航速度的`rotateByYawRateAsync`建立AirSim内部的直接位置保持，再组装完整任务Runtime；此调用保持当前位置，不执行转向。已有API控制权直接复用，停止时不重新解锁。确认停稳同时检查相对参考位置的误差与速度，日志输出参考高度和实际高度。普通悬停失败继续重试HOLD接管并保持`stopping`，只有确认AirSim断线才转入地图重连准备。参考位置在接管开始时采集，AirSim实际保持点在RPC执行时采集，仍可能存在制动、通信与进程交接造成的位移。
运动RPC按`airsim.move_timeout_s`设置等待时间，状态查询和只读心跳保留各自的短超时。两种RPC由同一飞行控制线程串行调用；异步调用读取实际结果及RPC错误，不把等待结束等同于运动成功。
地图断线后，HTTP和日志仍可用，心跳推动自动重连；新地图就绪后等待新任务，不继续旧任务。
心跳与状态接口互相独立，查询状态不会额外探测AirSim。无法检测未出现断线或RPC错误的无缝地图替换。

按Ctrl+C退出服务时也会尝试取消遗留运动并悬停；AirSim不可达时会记录无法确认停止。
终止执行进程不能取消远端模型计算，但其结果不会进入新运行环境。强制中断的实验可能缺少阶段末尾才落盘的控制CSV或最终结果，已写入的图像和日志保留。
浏览器接口和真实子进程已用离线替身验证；实际AirSim、真实模型和前端地图切换仍需联调。
前端对接使用[完整API约定](docs/API设计.md)：包含请求字段、完整返回示例、错误码、日志游标、按钮状态和浏览器调用示例。原`python run_airsim_cli.py`交互入口继续保留。

Linux需使用自己的Python环境安装依赖，不能复制Windows虚拟环境。后端部署到Linux、AirSim运行在另一台机器时，`airsim.host`填写仿真器机器IP；前端访问的是后端机器的HTTP地址，两者不同。Linux离线验证及实际仿真器未验证范围见[后端实施记录](docs/SERVER_BACKEND.md)。

## 位置保持与任务结束（2026-10-27）

服务器起飞准备、停止任务、任务收尾和空闲时共用固定世界XYZ/yaw的保持服务。执行线程根据位置误差和实测速度发送有加速度/jerk限制的速度指令；模型等待、独立采图和确认间隔也持续维护保持。输入线程只收命令，采图线程只读图像，不取得飞行控制权。正式采图连接按首次需要创建，基础动作不会启动采图线程。

保持确认使用`motion.settle_time_s`完整时间窗：位置相对固定参考及窗内任意两点的偏移不超过`motion.position_tolerance_m`，朝向偏移不超过`motion.yaw_tolerance_deg`。允许容差内的小幅漂移，不要求瞬时速度严格为零；绕大圈后回到原位不能通过。图像采集时仍保持并复查观测条件。

基础阶段到位后才进入下一阶段；后端只在任务收尾保持成功后输出最终报告和完成事件。保持失败仍报错，不把接口返回或不稳定状态显示为成功。启动读取连续推进的仿真状态；起飞日志记录起点高度、实际爬升和原生结果。原生起飞未确认但实际已经爬升时，仍须通过位置保持才能就绪。

HTTP路径、输入输出、状态码和状态枚举均不变。模型仍返回5个新增航点、bbox与最多5个表面点、完成true/false；所有角色关闭思考。需要同步`planner/`、`config/`和本文；无需前端改动。离线验证和实飞结果分别记录于[本次修改说明](docs/FLIGHT_COMPLETION_REPAIR_2026-10-27.md)。
