# 快慢双系统与滑动窗口闭环方案

本文档说明在当前 AirSim 闭环基础上，如何引入快慢双系统与滑动窗口 Qwen 规划，以提升在线效率并减少目标附近飞过问题。方案目标是新增能力，而不是继续在已有主循环中补零散逻辑；旧版非滑动窗口入口和现有滑动窗口入口必须保持可用。

## 1. 当前闭环状态

当前项目主要有两个运行入口：

| 入口 | 用途 | Qwen 输出格式 | 当前执行方式 |
|---|---|---|---|
| `run_airsim_web.py` | 旧版稳定闭环 | 5 个累计 body-frame waypoint | 每步等待规划完成后执行整段 |
| `run_airsim_web_sliding_window.py` | 滑动窗口实验入口 | additional 增量 waypoint | 每步等待规划完成后执行队列中一小段 |

旧版闭环流程如下：

```text
任务输入
→ task parser 一次性解析 stage
→ target stage 抓 front/down RGB
→ 目标检测、完成判定、Qwen 规划并行
→ 等深度图补全 TargetDepth
→ completion done=True 切换 stage
→ done=False 执行 Qwen 输出的累计 waypoint
→ 下一步重新抓图、重新规划
```

现有滑动窗口入口已经完成了关键数据结构转换：

```text
Qwen 输入：front/down RGB + instruction + pending incremental body-frame waypoints
Qwen 输出：additional incremental body-frame waypoints
运行队列：absolute world waypoints
执行入口：current pose 下的 cumulative body-frame waypoints
```

也就是说，现有滑动窗口已经有“轨迹队列”的雏形，但仍然不是完整快慢双系统。它的问题是：每一步仍然先等待 Qwen 返回，再执行一小段轨迹；执行期间没有真正持续消费队列，也没有在后台提前补轨迹。

## 2. 为什么需要快慢双系统

当前 Qwen 平均推理约 4 秒。如果每一步都等待 Qwen，则闭环效率上限被慢模型卡住。目标附近飞过的问题也和这一点有关：为了减少等待，旧版一次执行较长轨迹；但轨迹过长时，completion 无法在执行中途打断，就容易飞过目标。

快慢双系统的核心思想是：

```text
慢系统：低频、高延迟、语义和规划
快系统：高频、低延迟、轨迹消费和安全控制
```

慢系统负责：

```text
任务解析
目标检测 / VLM completion
Qwen 滑动窗口补轨迹
候选轨迹/世界模型选择
重定位
stage 切换决策
```

快系统负责：

```text
持续执行 world waypoint 队列
每次只执行 1-2 个短 waypoint
监控队列剩余量
碰撞后后退恢复
收到 done / abort / stage change 后立即清空队列
```

最终期望从：

```text
抓图 → 等 Qwen → 执行 → 抓图 → 等 Qwen → 执行
```

变成：

```text
快系统持续执行队列
慢系统后台周期性看图、判定完成、补充队列
```

## 3. 推荐总体架构

不要直接重写 `run_airsim_web.py`，也不要破坏现有 `run_airsim_web_sliding_window.py`。推荐新增第三个入口和两个模块：

```text
agent/runtime/trajectory_queue.py
agent/runtime/fast_slow_controller.py
run_airsim_web_fast_slow.py
```

三个入口职责如下：

| 入口 | 是否保留 | 说明 |
|---|---|---|
| `run_airsim_web.py` | 保留不动 | 旧版非滑动窗口闭环，作为稳定基线 |
| `run_airsim_web_sliding_window.py` | 保留不动 | 当前滑动窗口分步闭环，作为过渡基线 |
| `run_airsim_web_fast_slow.py` | 新增 | 快慢双系统实验入口 |

这样做的好处是：

```text
旧 Qwen / 旧 planner 不受影响
现有滑动窗口入口不受影响
快慢系统可以快速试错
出了问题可以立即回退旧入口
```

## 4. 核心数据结构

### 4.1 队列内部统一存 absolute world waypoint

快慢系统中，轨迹队列统一存绝对世界坐标点，而不是直接存 body-frame 增量。Qwen 的输入输出仍然是以提交规划时当前正视图为锚点的 incremental body waypoint；队列负责把它固化成世界坐标，避免 Qwen 推理期间无人机移动导致参考系漂移。

推荐队列格式：

```python
world_waypoints = [
    [x_world, y_world, z_world],
    [x_world, y_world, z_world],
    ...
]
```

### 4.2 Qwen 输入输出使用 incremental body-frame

训练好的滑动窗口 Qwen 使用：

```text
输入 pending：相对于提交规划时当前 pose/yaw 的 incremental body waypoint
输出 additional：继续补充的 incremental body waypoint
```

运行时转换流程：

```text
world queue
→ 根据提交规划时 current pose/yaw 转 cumulative body
→ cumulative body 转 incremental body
→ 作为 pending 输入 Qwen

Qwen additional incremental
→ 追加到 pending 末尾得到 cumulative body
→ 根据提交规划时 current pose/yaw 转 world
→ append 到 world queue
```

### 4.3 AirSim 执行使用累计 body-frame

快系统每次从 world queue 取前 N 个点，按执行时当前 pose/yaw 转成 cumulative body waypoint：

```text
world queue first N
→ current pose/yaw 下的 cumulative body waypoint
→ execute_waypoints
→ 成功后 pop N 个 world waypoint
```

这样可以最大程度复用现有执行器。

## 5. 快慢系统运行时序

### 5.1 启动阶段

```text
1. 启动 Web Dashboard
2. 连接 AirSim，arm/takeoff
3. 启动 FrameCapturer
4. warmup task parser / completion / sliding Qwen
5. 等待任务输入
6. task parser 解析 stage
7. 初始化 FastSlowController
```

### 5.2 target stage 时序

```text
1. 清空上一 stage 队列
2. 慢系统抓 front/down RGB
3. completion 判断当前 stage 是否已完成
4. 如果完成：清空队列，切 stage
5. 如果未完成且队列为空：同步调用一次 Qwen 生成初始队列
6. 快系统开始消费队列
7. 当队列剩余不足时，慢系统后台异步补轨迹
8. 慢系统周期性重新抓图并做 completion
9. 一旦 completion done=True：停止快系统，清空队列，切 stage
```

### 5.3 action stage 时序

action stage 不走快慢队列，仍然直接执行：

```text
up / down / left / right / forward / backward
```

执行前必须清空 target 队列，避免上一个目标阶段残留轨迹。

## 6. 调度策略

### 6.1 快系统消费策略

建议一天内先实现保守版本：

```text
EXECUTE_COUNT = 1
```

也就是每次只执行队列中的 1 个 waypoint。这样响应最及时，目标附近不容易飞过。等稳定后再改成 2。

快系统循环：

```text
while stage_active:
    if queue empty:
        wait briefly
        continue

    current_pose = client.get_pose()
    exec_wp = queue.first(EXECUTE_COUNT) -> cumulative body
    execute_waypoints(exec_wp)

    if collided:
        collision_recovery.recover()
        clear queue or keep queue based on config

    queue.pop(EXECUTE_COUNT)
```

注意：AirSim RPC 不是严格线程安全。建议第一版不要让快系统和慢系统同时调用运动类 RPC。慢系统只抓图和规划，快系统只执行运动。抓图如果和运动冲突，可以通过锁保护。

### 6.2 慢系统补轨迹策略

补轨迹触发条件：

```text
queue_length <= LOW_WATERMARK
或
estimated_remaining_exec_time <= QWEN_AVG_TIME + SAFETY_MARGIN
```

建议配置：

```yaml
FAST_SLOW:
  ENABLED: true
  LOW_WATERMARK: 3
  HIGH_WATERMARK: 8
  EXECUTE_COUNT: 1
  QWEN_AVG_TIME_S: 4.2
  SAFETY_MARGIN_S: 1.0
```

第一版可以只用 `queue_length <= 3`，不要急着加复杂速度估计。越简单越稳。

### 6.3 completion 检查策略

completion 不需要每执行一个 waypoint 都跑 VLM，否则慢。建议：

```text
每隔 COMPLETION_INTERVAL_S 秒检查一次
或目标深度变化明显时检查一次
或队列即将耗尽时检查一次
```

建议配置：

```yaml
FAST_SLOW:
  COMPLETION_INTERVAL_S: 1.5
```

目标附近可以提高检查频率：

```text
如果上一次目标深度 < 1.5 * STOP_DEPTH_THRESHOLD
COMPLETION_INTERVAL_S 临时降到 0.8s
```

这个是调度策略，不要写死成 completion 规则。

## 7. 一天内可落地的最小实现版本

不要一上来追求最完整。明天 Qwen 微调完后，最小可用版本建议这样做：

### 阶段 A：保持现有滑窗入口稳定

目标：

```text
确认 run_airsim_web_sliding_window.py 能调用新 LoRA
确认 QwenSliding 输出 additional incremental waypoint
确认队列 append / execute / pop 正常
```

不改旧入口。

### 阶段 B：新增 fast_slow 入口

新增：

```text
run_airsim_web_fast_slow.py
agent/runtime/fast_slow_controller.py
```

先复用：

```text
SlidingWindowQwenPlanner
SlidingWindowTrajectoryQueue
completion_checker
collision_recovery
TaskManager
```

第一版逻辑：

```text
target stage 开始
→ completion 检查一次
→ 未完成则 Qwen 同步生成初始队列
→ 循环执行一个 waypoint
→ 每执行一个 waypoint 后，如果队列 <=3，则异步补 Qwen
→ 每 1.5s 做一次 completion
→ done 后清空队列切 stage
```

这个版本已经比当前滑动窗口更快，因为 Qwen 补轨迹可以和执行重叠。

### 阶段 C：再优化异步补轨迹

需要一个 `planning_future` 状态：

```text
planning_future is None：没有后台 Qwen
planning_future running：不要重复提交
planning_future done：取结果 append queue
```

伪代码：

```python
if need_replan and planning_future is None:
    planning_future = executor.submit(plan_with_current_frame_and_pending)

if planning_future and planning_future.done():
    result = planning_future.result()
    queue.append_incremental_output(result.waypoints, plan_pose, plan_yaw)
    planning_future = None
```

重要点：Qwen 输出转换 world 时，必须使用提交规划时的 `plan_pose/plan_yaw`，不能用 Qwen 返回时的 pose，否则坐标会漂。

## 8. 与当前系统的变动关系

### 8.1 不应该改动的部分

以下文件不建议修改：

```text
run_airsim_web.py
```

原因：

```text
这是旧版稳定闭环入口
旧 Qwen 输出累计 waypoint
旧 API atomic planner 也依赖该入口
汇报前必须保留可回退路径
```

以下文件也不建议大改：

```text
run_airsim_web_sliding_window.py
```

原因：

```text
这是当前滑动窗口分步闭环基线
可以用于验证新 LoRA 是否可用
快慢系统出问题时仍可回退到它
```

### 8.2 可以新增的部分

推荐新增：

```text
agent/runtime/trajectory_queue.py
agent/runtime/fast_slow_controller.py
run_airsim_web_fast_slow.py
```

其中 `trajectory_queue.py` 可以先复用或包装 `SlidingWindowTrajectoryQueue`，不要复制太多逻辑。

### 8.3 可以小幅修改的部分

可以在 `config/default.yaml` 增加新配置，但默认关闭：

```yaml
FAST_SLOW:
  ENABLED: false
  LOW_WATERMARK: 3
  HIGH_WATERMARK: 8
  EXECUTE_COUNT: 1
  COMPLETION_INTERVAL_S: 1.5
  QWEN_AVG_TIME_S: 4.2
  SAFETY_MARGIN_S: 1.0
  CLEAR_QUEUE_ON_COLLISION: true

SLIDING_WINDOW:
  MAX_PENDING: 3
  MAX_ADDITIONAL: 5
  EXECUTE_COUNT: 1
  PLANNER_URL: ""
  PLANNER_MODEL: ""
  PLANNER_TIMEOUT: 120
  ENABLE_CANDIDATES: false
```

默认 `FAST_SLOW.ENABLED=false`，所以不会影响旧功能。

## 9. 兼容性说明

### 9.1 对非滑动窗口功能的影响

如果按本文方案新增入口和模块，不修改 `run_airsim_web.py`，则非滑动窗口功能不受影响：

```text
旧 Qwen cumulative waypoint 不变
旧 execute_waypoints 不变；滑窗快慢系统继续复用该执行入口
旧 completion / detector / task parser 不变
旧 candidate pipeline 不变
```

运行方式仍然是：

```bash
python run_airsim_web.py
```

### 9.2 对现有滑动窗口功能的影响

如果不修改 `run_airsim_web_sliding_window.py`，现有滑动窗口分步闭环也不受影响：

```bash
python run_airsim_web_sliding_window.py
```

它仍然可以作为新 LoRA 的最小验证入口。

### 9.3 新快慢系统入口

新功能通过独立入口运行：

```bash
python run_airsim_web_fast_slow.py
```

如果快慢系统出现问题，立即退回：

```bash
python run_airsim_web_sliding_window.py
```

或：

```bash
python run_airsim_web.py
```

## 10. 关键风险和规避

### 10.1 AirSim RPC 并发风险

风险：

```text
快系统执行 moveOnPathAsync 时，慢系统同时 capture_views，可能造成 RPC 阻塞或延迟异常。
```

规避：

```text
第一版加 client_rpc_lock
运动 RPC 和抓图 RPC 不完全并发
先保证稳定，再逐步放开抓图并发
```

如果完全加锁，效率提升会小一些，但仍然能实现 Qwen 推理和执行重叠。

### 10.2 规划 pose 和返回 pose 不一致

风险：

```text
Qwen 提交时无人机在 A 点，返回时已经飞到 B 点。
如果用 B 点把 additional 转 world，会导致轨迹错位。
```

规避：

```text
提交 Qwen 时保存 plan_pose / plan_yaw
Qwen 返回后用 plan_pose / plan_yaw 转 world
```

这是快慢系统最重要的正确性约束。

### 10.3 completion 延迟导致过冲

风险：

```text
completion 是慢系统，done=True 返回时无人机可能已经继续执行了一个 waypoint。
```

规避：

```text
EXECUTE_COUNT=1
单个 waypoint 距离由滑窗训练控制在较短范围
目标接近时提高 completion 检查频率
done=True 立即清空队列
```

### 10.4 队列被旧 stage 污染

风险：

```text
stage 切换后继续执行上一目标的 world waypoint。
```

规避：

```text
action stage 前 clear queue
target stage 变化时 clear queue
completion done=True clear queue
collision recovery 后按配置 clear queue
```

### 10.5 新 LoRA 输出格式不稳定

风险：

```text
模型偶尔输出 cumulative 或文本解释。
```

规避：

```text
保留严格 JSON parser
解析失败不追加队列
队列不足时暂停快系统等待下一次规划
终端打印 raw_output 前 300 字符用于定位
```

## 11. 汇报表述建议

可以这样讲：

```text
当前闭环已经实现 completion 与 Qwen planning 的步内并行，但仍然是等待式闭环。
本周进一步设计快慢双系统：慢系统负责语义理解、任务完成判定和滑动窗口 Qwen 补轨迹；
快系统负责持续消费 world waypoint 队列和安全执行。
滑动窗口 Qwen 的 pending/additional 增量格式正是为了支持这个异步队列机制。
为了保证稳定性，新系统将作为独立入口接入，不影响旧版非滑动窗口闭环和当前滑动窗口基线。
```

## 12. 推荐实施顺序

一天内建议只做下面这些：

```text
1. 先用 run_airsim_web_sliding_window.py 验证明早微调好的 LoRA 能正常输出增量 waypoint。
2. 新增 run_airsim_web_fast_slow.py，不改旧入口。
3. 第一版 fast_slow 只做 target stage，action stage 继续直接执行。
4. EXECUTE_COUNT 固定为 1，LOW_WATERMARK 固定为 3。
5. 只实现一个后台 planning_future，不做复杂多任务调度。
6. completion 每 1.5s 检查一次，done 后清空队列切 stage。
7. 如果任何异常，直接退回 run_airsim_web_sliding_window.py 做汇报 demo。
```

这条路线的关键不是一次写完最复杂的系统，而是在保留旧功能的前提下，把“Qwen 推理”和“无人机执行”真正重叠起来。只要这一步跑通，效率提升就能在日志里体现出来。
