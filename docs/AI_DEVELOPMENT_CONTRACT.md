# Planner开发与并行协作规范

适用项目：base_planner及其后续扩展。本文可随修改需求一起提供给AI或开发人员。

## 1. 每次开发前给AI的提示词

> 请遵守本文件进行开发。先阅读当前实现，说明本次涉及哪些模块、是否修改公共接口，然后在对应目录中实现并验证。保持任务调度、任务流程、业务能力、外部服务适配和飞行执行之间的边界。不要为了快速实现把新逻辑堆进CLI、bootstrap或navigation.py。优先复用现有接口；确需新增接口时，定义明确的输入、输出、错误和生命周期。不得擅自改变其他任务的行为或覆盖他人改动。结束时说明修改文件、接口兼容性、测试结果和未验证事项。除非本次需求明确要求，不自动提交、合并、删除旧模块或扩展为无关重构。

本文约束代码组织和交付方式，不代替本次功能需求。明确的新需求优先；如需突破架构边界，先说明原因和最小调整方案，不得静默绕过规范。

## 2. 核心原则

1. 一个文件围绕一个职责。不同任务分别实现Workflow，共用观测、轨迹变换和执行服务。
2. Mission负责阶段顺序；Workflow负责阶段内流程；Capability负责可复用业务能力；Adapter负责外部系统调用。
3. 依赖通过构造参数显式注入，不能通过全局变量、导入时注册、万能Context或共享可变字典传递。
4. 先设计最小接口，再实现功能。不要创建没有实际使用方的庞大插件框架。
5. 保留服务器模型与DeepSeek等后端的替换能力，不把某个模型名称写入通用业务判断。
6. 明确区分轨迹执行完毕、模型宣称完成、几何验证完成、失败和未确认。API正常返回不能等同于任务成功。

## 3. 模块放置规则

| 目录/文件 | 放什么 | 不应放什么 |
|---|---|---|
| `run_airsim_cli.py` | 参数解析、启动、用户输入、结果展示 | 提示词、坐标计算、任务策略、模型HTTP调用 |
| `config/` | YAML配置、类型定义、加载和校验 | 飞行流程和业务分支 |
| `planner/bootstrap.py` | 选择具体实现、注入依赖、组装应用 | 执行循环、模型输出解析、任务成功判断 |
| `planner/application/` | 解析后任务校验、阶段调度、Workflow路由 | RGB处理、AirSim API、单个任务的内部策略 |
| `planner/domain/` | 强类型任务、位姿、观测、轨迹、状态和结果 | 网络请求、设备调用、配置文件读取 |
| `planner/workflows/` | 各任务的状态转换、调用顺序、重试和退出条件 | HTTP请求、图像编码、底层控制、完整检测算法 |
| `planner/capabilities/` | 检测、记忆、完成判定等可复用业务能力 | 直接耦合某一家模型SDK；替代整个Workflow |
| `planner/services/` | 坐标变换、轨迹校验、执行协调等共享逻辑 | 特定任务的大量条件分支 |
| `planner/services/motion/` | 航点到执行段的运动策略、后续平滑算法 | 任务解析、语义目标识别 |
| `planner/ports/` | 对模型、观测、飞行器、检测/存储等依赖的类型化接口 | 具体HTTP客户端和AirSim实现 |
| `planner/adapters/` | 实现Port，完成外部协议和内部类型之间的转换 | 决定整个任务流程 |
| `planner/extensions/` | 白名单注册、扩展工厂和装配入口 | 根据模型返回的字符串动态导入或执行代码 |
| `tests/` | 单元、接口契约、模拟集成测试 | 默认连接真实模型或触发无人机起飞 |
| `docs/` | 架构、协议、使用说明、迁移说明 | API key和机器私有信息 |
| `output/` | 运行日志、图像及评测产物 | 需要版本管理的代码和配置模板 |

新增目录必须有明确职责。沿用snake_case文件名、PascalCase类名和Python 3.10类型标注。不要新建`misc.py`、`all_utils.py`等无边界文件。

## 4. 依赖边界

运行调用顺序：

```text
CLI → Application → MissionRunner → WorkflowRouter → Workflow
                                                    ↓
                                            Capability / Service
                                                    ↓
                                                   Port
                                                    ↑ 实现
                                                  Adapter
```

- Domain不依赖Application、Workflow、Adapter或配置加载器。
- Workflow、Capability、Service依赖Domain和必要的Port，不导入具体Adapter。
- Application负责阶段级调度，不了解图像、深度、Qwen或AirSim细节。
- Adapter可以使用Domain和纯计算辅助模块，不反向调用Workflow或Application。
- `bootstrap.py`是允许同时认识接口与具体实现的组装位置。规模增长时按功能拆分组装函数，不将其变成第二个运行时。
- 通用图像编码、HTTP传输等如果被多个Adapter使用，应提取到适配层内部的小模块，避免Adapter相互调用私有函数。
- MotionPlanner属于内部策略，不为了统一而强行放入外部Port。

## 5. 新任务与任务分支

当前仅有`navigation`。任务解析器只能返回预先定义的有限任务类型；不能让模型自由选择Python文件或自行编排模块。

增加任务的标准步骤：

1. 在Domain中定义TaskKind和该任务的专用参数类型。扩展MissionStage参数类型及校验，不使用万能`params: dict`代替类型设计。
2. 同步任务解析prompt、返回Schema和task_factory；拒绝未知类型、未知关键参数和非法值。
3. 在`workflows/<task_name>.py`实现Workflow，满足统一的阶段输入和结果接口。
4. 可复用能力通过接口注入。例如巡检和导航可以共享检测、记忆与执行服务，不复制整套实现。
5. 在组装入口显式注册`TaskKind → Workflow`，由Router确定性选择。不要在MissionRunner中添加任务专用大段`if/elif`。
6. 在任务执行前校验所有阶段及必要能力；缺失必需能力时报告不可用，不静默退化成另一类任务。
7. 测试该任务独立运行、与其他任务串联、失败传播及未知任务拒绝。

例如后续导航、巡检、跟随可以是不同Workflow，按需求调用相同的检测/记忆能力。它们共享接口，但不共享彼此的执行循环。

阶段之间确需传递目标或地图时，定义专用的不可变结果和显式交接接口，注明数据有效期。不要把整个上游内部对象塞入全局Context。

## 6. 检测、记忆、完成判断应如何接入

| 新功能 | 推荐位置及边界 |
|---|---|
| GroundingDINO目标检测 | `ports/target_detector.py`定义接口；`adapters/detection/`实现请求；目标筛选/关联逻辑放`capabilities/targeting/` |
| 任务记忆 | `domain/`定义记录类型；`capabilities/memory/`管理任务范围和更新规则；有存储需求再定义Port及`adapters/memory/` |
| 完成判定 | 独立类型化接口，返回状态、依据及剩余动作；模型调用在Adapter，跨证据判定策略在Capability |
| 新模型后端 | `adapters/trajectory_planner/`新增或复用协议适配；通过配置和组装选择，不能改写Workflow来识别模型名 |
| 轨迹平滑 | `services/motion/`新增策略，保持输入世界轨迹、输出执行段的约定 |
| 新模拟器 | `adapters/<simulator>/`实现观测与Vehicle接口，保留Domain坐标约定 |

每项能力注明：输入、输出、错误类型、超时、是否有状态、任务开始/结束时如何初始化或清理。没有被本任务启用的能力不应启动线程、发请求或影响结果。

## 7. 必须保护的数据协议

- 轨迹输入为当前RGB和同视角深度；保持相机内外参与位姿来源明确。不同分辨率不能直接按同一像素索引处理。
- 当前执行端接受1～配置上限个四维点，默认上限5；不得把空轨迹默认为成功。
- 每点为`[dx, dy, dz, dyaw_deg]`，位移单位米、旋转单位度。
- 第一段相对当前水平机体系；后续段相对上一预测姿态。每段先按上一yaw转换平移，再累计该段dyaw。
- `+dx`前、`+dy`右、NED的`+dz`下、`-dz`上，正yaw右转。相机Pitch不改变运动坐标符号。
- 平移和观察朝向独立，不根据平移向量擅自覆盖模型yaw。
- 纯旋转必须明确执行yaw控制并校验结果；同步运动模式复用零平移的时间曲线，旧linear模式使用专用旋转API，不能用已到位的位置API代替旋转。
- 相对轨迹与世界轨迹分别校验，不能通过放宽解析绕过执行安全检查。
- 训练协议、推理prompt、服务器解析和本地执行语义必须对齐。修改协议时列明四者影响；不能只改一端并声称兼容。

## 8. 循环流程与退出规则

Workflow需要明确观察、规划、执行、复核、结束或失败状态。循环必须有配置化上限和可解释的退出结果，不允许无条件无限重试。

- 请求失败、非法返回、目标不确定、达到上限和动作执行失败分别记录原因。
- 复核应结合任务起点、当前观测和必要执行记录，避免重复执行相对命令。
- 模型声称完成应标注证据来源，不能标成独立几何验证。
- 保持阶段之间的状态隔离，不把上一个任务目标误带入下一个任务。
- 飞行执行失败应通过统一执行服务取消或悬停；Workflow不直接调用AirSim。
- 重试、并发模型请求、背景录制需要明确资源所有权和退出清理；禁止并发抢占同一飞行控制权。

## 9. 多人/多AI并行开发与合并

默认协作指各自开发后合并代码，不代表同时运行多套飞行控制程序。

### 开始前

为每项工作填写：

```text
任务名称：
基线分支/提交：
负责人及分支：
负责目录/文件：
需要的公共接口：
是否改变配置或协议：
与其他任务的依赖：
验收场景：
```

每人使用独立分支，必要时用独立worktree。不要在同一个工作目录中同时切换分支。保留他人的未提交改动，不得用强制重置解决冲突。

### 公共接口先行

- `domain/`、`ports/`、配置Schema、TaskKind、Router注册和`bootstrap.py`属于共享集成区域。
- 有多人依赖的接口先提交最小契约变更，再由各任务基于该版本开发。接口负责人协调名称、类型、错误和兼容性。
- 无依赖的任务可先各自开发，公共注册改动由集成者统一合并。
- 不同任务不要各自创建重复的Registry、Configuration或MissionContext。
- 协作状态放在任务说明或PR，不放在模型prompt或可执行业务代码中。

### 合并顺序

```text
公共类型/接口 → 独立能力与Adapter → Workflow → 配置/注册/CLI → 集成验证
```

小提交保持单一主题。合并冲突需检查双方行为和接口语义，不能机械选整份“我的/对方的文件”。接口变化必须同步更新调用方、Fake实现和契约测试。

合并后至少验证：旧任务仍可运行、新任务单独运行、多个阶段串联、缺失能力时明确失败、退出时资源清理。单个分支测试通过不代表合并版本通过。

## 10. 控制文件规模

行数是提醒，不是为了拆分而拆分的硬目标：

- 普通模块超过约300行，或Workflow超过约200行时，应检查是否混入其他职责。
- 一个函数同时处理请求、图像编码、解析、几何和执行时，即使很短也应拆分。
- 不通过通配导入、动态转发或把代码搬进`helpers.py`掩盖原有耦合。
- 优先按协议解析、后端请求、进度评估、几何计算等职责拆分；不要按“文件上半段/下半段”拆。

## 11. 验证与交付

测试应覆盖行为和边界，而不是仅复述实现：

- 单元测试：坐标符号、yaw累计、角度跨界、可变点数、非法数据。
- 契约测试：模型请求/返回、TaskKind参数、可替换Adapter满足同一接口。
- 模拟集成测试：Workflow多轮继续、完成、阻塞、步数上限、执行失败后的处理。
- 实机/仿真测试单独标识；没有连接AirSim或真实API时，不能声称实飞通过。

常用本地检查：`python -m pytest tests -q`。日志不得输出密钥、Authorization或图片base64；配置中实际密钥不得提交。

每次交付必须包含：实现的行为、模块归属、公共接口/协议变更、兼容影响、验证结果、未验证内容以及需要的启动/配置说明。

## 12. 当前实现的已知边界（2026-09-21）

以下是现状，不是应继续复制的设计范例：

- 当前仅注册navigation任务；extensions还是扩展骨架，不能描述为已具备完整插件系统。
- `qwen_vl_planner.py`同时服务服务器模型和DeepSeek，名称有历史遗留。未来重命名应作为明确兼容迁移处理。
- 进度复核结果已移入Domain，Workflow通过类型化ProgressReviewer Port注入；后续复核器继续遵守该边界。
- `progress_review.py`复用其他Adapter的私有图像编码函数。涉及共享客户端重构时应提取公共编码工具。
- 当前复核图像和无人机位姿不足以保证任意斜视下的几何完成判断；不要声称它已经完成严格几何验证。
- 当前服务端模式默认单段执行，DeepSeek配置默认启用多轮复核；不能在修改新流程时静默改变另一模式。
- `MissionResult.success`当前同时承载执行成功和复核成功。后续扩展结果协议时应引入类型化完成依据，逐步替代CLI对临时字典字段的判断。
- 进度复核接口可独立注入，当前组装仍复用轨迹规划后端；新增任务或后端时应显式选择，不应形成硬绑定。

修复这些边界应随相关需求有范围地进行，不要求每次开发都先进行全项目重构。
