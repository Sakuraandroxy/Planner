# 目标架构：代码归属的判据与改动范围

现在靠目录名判断不了一段代码该写在哪。`adapters`、`services`、`capabilities` 三者的语义有重叠，同一件事经常有两个说得通的落点。这份文档给出一条可执行的判据，据此把共享代码分成六类，并给出改四类东西时各自要动哪些位置。

## 什么会变，什么不会变

分层要沿变化的方向切。下面五项现在确定。

| 项 | 现在 | 会不会变 |
| --- | --- | --- |
| 载具 | 无人机（可横移）、阿克曼无人车（不能横移） | 不变，只有这两种 |
| 仿真器 | ProjectAirSim（UE5）、AirSim（UE4） | 会变，可能加第三套 |
| 任务 | 数值动作、视觉目标导航、自由导航 | 会变，会加新任务 |
| 地图 | 场景数据 | 会变，持续新增 |
| 模型端点 | 轨迹规划、目标检测、指令解析、完成判定 | 会变，可能换供应商或模型 |

载具固定影响两处：契约层只声明这两种载具，计算层的运动律不必为更多动力学预留分支。

## 判据

两个问题，问代码本身，不问它叫什么。

1. 这段代码是否记住上一次的状态：开线程、持锁、占设备、读时钟、缓存上次结果。
2. 这段代码是否认识某一类具体任务：会不会出现"视觉目标""自由导航"这样的名词。

两个问题相互独立，得到四个格子。

|  | 不认识具体任务 | 认识具体任务 |
| --- | --- | --- |
| 有状态、读时钟 | 执行层 | 任务层、装配层 |
| 无状态、纯变换 | 计算层 | 任务层 |

- 有状态、不认识任务：执行层。谁在什么时候给载具发指令属于这一层。
- 无状态、不认识任务：计算层。给同样的输入得同样的输出。
- 无状态、认识任务：任务层里跟单个任务绑定的判断，例如完成判定、参数准入。
- 有状态、认识任务：分两处。任务包里的阶段编排只认一个任务；装配层的路由与后端状态机认所有任务，但不归任何一个任务。

表格覆盖不了另外两类代码，因为它们没有计算过程。

- 契约层只有类型与接口声明，不做变换，所以不是计算层。
- 入口层在进程边界上，只做请求翻译与遥测读出，不属于上面任何一格。

`capabilities` 现在同时装着计算层与任务层的内容：深度几何和完成判定分属两个格子，住在同一个目录下。

判据在同时含状态与纯计算的模块上要人工切开。实例是续规划滑窗：`capabilities/sliding_window/worker.py` 里有 `threading.Condition`，`services/planning_window.py` 把它包一层。按第一个问题切：补规划策略留在计算层，在途请求管理进执行层。

## 六类代码

### 契约层 `planner/domain/`、`planner/ports/`

放全栈共用的定义：位姿与坐标系约定、观测样本、轨迹与运动段、任务与阶段、能力名、载具声明、完成证据、异常分类，以及全部端口的 `Protocol`。

不放逻辑。新增工具函数放计算层，这一层只收类型定义与不变量校验。

端口声明放这里，是为了让上层依赖声明而不是依赖实现。执行层需要"能执行一段运动"和"能取一帧观测"，不需要知道谁提供这两项。

载具声明写的是运动学能力，不是型号：无人机可横移，无人车只能前后移动加转向。声明里放运动学类别、物理包络、相机挂点。能否横移只由计算层读这个类别判断一次，执行层与任务层都不判断。

代价是这一层被所有模块引用，任何改动波及其他五层。所以准入要严格：看不懂是不是类型定义的东西，不放进来。

### 计算层 `planner/capabilities/` 的纯函数部分

相同输入得到相同结果，不读时钟、不开线程、不碰设备与网络。内容包括几何变换与深度反投影、运动律（插值、航向指令、转弯限速、加减速限幅）、序列合法性校验、从观测中量出距离与角度。

判据能直接检验：能不能脱离仿真器单独跑。写不出这样的测试，说明它偷偷用了别处的状态。现有的扇面测距、位姿换算、目标表面估计都满足这一点，现在分散在 `capabilities/` 与 `services/` 两个包里。

运动律里唯一按载具分叉的地方是能否横移。无人机走全向分支，无人车走前后加转向分支，越点走廊在车这一侧放宽到 0.6 m。这个数值现在写在 `simulators/projectairsim/rover.py` 的 `ROVER_PASSED_LATERAL_TOLERANCE_M` 里，目标位置是本层。

### 执行层 `planner/services/`、`planner/simulator/`

有状态、读时钟，但不认识任何具体任务。内容是控制权、执行器、航点队列、续规划滑窗、位置保持、碰撞退避、帧与遥测的汇、受限的后台任务。只依赖契约层的端口声明，端口实现由装配层插进来。

控制权是这一层唯一的硬约束：任一时刻每台载具只有一个持有者能下指令，观测采集、位置保持、轨迹执行都只是临时持有者，交接要有停稳与确认的协议。现在的实现用线程归属加检查点间接表达这件事，没有把它命名成一个概念，所以"会不会有第二个地方在发速度指令"只能靠读代码回答。

碰撞退避由这一层在检查点触发，任务层不编排它。接触发生时后退、清空队列、把控制权交回任务，三类任务因此拿到同一套行为。

### 任务层 `planner/workflows/`

每个任务一个包，放六样东西：参数定义与解码、准入检查、阶段编排、该任务自己的判断、交给模型的上下文、结束证据的形状。

另一部分是公共编排，放三类任务共用、但不属于任何单个任务的流程：连续跟随循环、失败恢复、预算计数、终止判定、证据汇总。公共编排允许知道"任务"这个概念，不允许出现具体任务名，只接收参数与钩子。

任务包之间不互相引用。代价是公共部分必须往上抽，好处是删掉一个任务不牵连其他任务。

现在没有这一层。碰撞恢复在两个任务里各写了一份镜像代码，原因就在这里：可选项只有复制，或者让两个任务互相引用，而后者被禁止。

### 装配层 `planner/application/`

唯一同时拿到任务和引擎的地方。四件事：确定本次跑什么（任务、载具、地图、规划器）、把请求路由到对应工作流、管后端状态机与命令队列、按配置造外部端点与检测器。

可跑哪些任务也在这里定：`TASK_REQUIREMENTS` 声明每类任务需要哪几个端口槽位，`SimulatorPorts.available_tasks()` 按实际填上的槽位求出交集，交集决定接口能接受哪些任务、控制台显示哪些按钮。

这一层要在构造期就能失败。少接一根线当场报错，不要等到跑了几小时才表现为行为异常。

### 入口层 `planner/adapters/http/`、`console/`

系统入站的一侧：HTTP 路由、视频流、浏览器控制台、命令行、无头批处理。只做两件事，把外部请求翻译成装配层的命令，把遥测读出来显示。

状态机在装配层，状态到状态码的映射在入口层。这条线现在大致成立，但 `application/server_controller.py` 有 1132 行，同时管状态机、换图、天气、外观、配置档切换，线并不严格。

## 六类之外

两类代码不归入上面六类，因为它们本身就是端口背后的东西。

- 引擎实现 `planner/simulators/<名称>/`。每个仿真器一个包，实现它确实支持的那些端口，能力由实现了哪些端口自动推导。两套现在支持的载具不一样：UE5 有无人机与车，UE4 只有无人机。所以引擎包里不出现任务名，任务包里不出现引擎名。
- 端口实现 `planner/adapters/` 里的模型端点、检测器、解析器、完成判定与它们的提示词。

## 现状与判据不符的位置

- `capabilities` 反向引用 `services`。纯函数方面有 `target_coordinates`、`trajectory_transform`；持状态方面有 `background_operation`、`observation_snapshot`、`model_calls`。`adapters` 也引用 `services` 的 `free_space`、`target_coordinates`、`trajectory_transform`。这些引用没引发运行错误，但让"计算层不依赖执行层"这句话不成立。
- 同一个概念定义两遍或三遍。`MotionLimits` 在 `domain/motion.py:38` 与 `services/segment_motion.py:21` 各一份，字段大半重合，`to_tracking_limits()` 做转换，加一个参数要在两处都改。`CameraView` 在 `ports/camera_view.py:7` 与 `ports/capabilities.py:20` 各一份，签名相同。世界位姿跟踪有三套，分别在 `services/motion/continuous.py`、`simulators/projectairsim/motion.py`、`simulators/airsim/motion_tracker.py`，差别只在执行器接口。碰撞后的后退与清队列重规划在两个任务里各写一遍，逻辑镜像。
- 任务侧的事写在引擎包里。`planner/simulator/ports.py:45` 的 `TASK_REQUIREMENTS` 声明的是"某类任务需要哪些端口"，属于任务侧的事实。
- 载具差异写在引擎包里。阿克曼车不能横移，处理办法是把 `passed_lateral_tolerance_m` 从 0.3 m 抬到 0.6 m（`simulators/projectairsim/rover.py:57`），越点走廊的放宽发生在端口实现内部。任务层确实不知道这件事，代价是同一份运动律换个调用方就换个行为。
- 新加一类任务要改八处。`TaskKind` 与 `TaskParameters`（`domain/mission.py`）、解码器注册表（`adapters/task_parser/tasks/__init__.py`）、准入校验（`application/mission_validator.py`）、工作流路由（`application/workflow_router.py`）、装配（`application/application.py`）、能力需求表（`simulator/ports.py`）、一段配置。这些位置之间没有统一约定，漏改一处只在跑到那个任务时才暴露。

## 依赖规则

五条，都能写成自动检查。

- 契约层不 import 其他任何层。
- 计算层不 import 执行层。
- 执行层只 import 契约层的端口声明，不 import `simulators/`。
- 任务包之间不互相引用。
- 装配层是唯一同时 import 任务与引擎的位置。

## 三条不变量

依赖方向之外，三条约束按不变量处理。它们被破坏时不会立刻报错，只在长时间运行后表现为难以复现的行为。

**控制权唯一。** 任一时刻每台载具只有一个持有者能下指令。典型破坏不是两处同时控制，而是某个后台循环在暂停期间还在发速度指令，表现为偶发的位置漂移。

**一帧观测齐备。** 观测交到下游时，图像、深度、位姿、仿真时间戳、内参必须同时存在，下游不再回查引擎。缺一项时，模型给的判断与当时的实际位姿错位，日志上还看不出时间差。

**完成要能复盘。** 任务报告完成时给出可测量的值和依据，不只是一个布尔值。没证据时任务可能在语义上误判完成，事后无法还原判断过程。

## 改四类东西时动哪里

计数口径：新增任务算"新建任务包"和"加配置"两处；新增引擎算"写进程配方"和"实现端口"两处。

| 变更 | 需修改 | 不应修改 | 怎么检验 |
| --- | --- | --- | --- |
| 新增一类任务 | 2 | 引擎、装配逻辑、入口层控件 | 引擎实现与界面代码里是否出现该任务名 |
| 新增一套仿真器 | 2 | 任务层、计算层、装配逻辑 | 任务包里是否出现引擎名，引擎实现里是否出现任务名 |
| 新增一张地图 | 0 | 全部代码 | 新地图是否引入"若为某图则如何"的分支 |
| 新增规划器或感知端点 | 2 | 任务包、引擎、入口层 | 任务包是否只要求"存在一个规划器" |

- **新增一类任务**（比如跟随某个人）：新建一个任务包，写参数、解码、准入、阶段、判定、证据形状，声明需要哪些端口，加一段配置。控制台按钮由端口交集推出来，引擎侧、装配逻辑、入口层都不用动。现在做同一件事要改八处，见上一节。
- **新增一套仿真器**：写进程配方（启动、就绪探针、必要时用子进程隔离依赖冲突），实现它确实支持的端口，能力由实现的端口自动推出。任务层和计算层不动。
- **新增一张地图**：只写数据，包括场景、出生点、相机挂点、可行驶区域、车道先验、限速、外观。现有三个地图已经做到，当作约束保持。
- **新增一个规划器或感知端点**：实现对应端口，在配置里选中。提示词属于实现内部，不要提成公共资产。两个任务共用一份提示词时，改一个会让另一个的行为跟着变。
- **新增一种载具**：不在计划内。两种载具的运动学已经定死，眼下不做预留。要动的是把"车不能横移"这件事从 `rover.py` 挪到契约层的载具声明里，越点走廊的默认值跟着类别走。

## 没有采纳的做法

| 做法 | 不采纳的原因 |
| --- | --- |
| 入口点插件自动发现 | "这次到底加载了哪些实现"没法直观确认。调试要能回答这个问题，注册不能省 |
| 拆分微服务 | 控制回路是毫秒级闭环节拍，跨进程通信会把同步语义换成重试与超时语义。只在引擎客户端库互相冲突时付出这个代价，现有实现也只为此给 UE4 起了子进程 |
| 用事件总线解耦全部模块 | 控制权要求同步、有顺序的语义，异步消息与之相反 |
| 用通用有向图描述全部任务流程 | 三类任务的差别在语义不在拓扑：什么算到达、什么时候该停、失败怎么理解。图之外的判定逻辑照样要写，只是多一层翻译 |
| 共享提示词 | 两个任务的失败会互相传染 |

## 迁移顺序

不推倒重写。前两步只搬位置，不改行为。

| 步骤 | 做什么 | 前置与风险 |
| --- | --- | --- |
| 1 | 把端口声明集中到一处，写清每个端口的语义，以及"没实现它意味着什么" | 后面所有边界都以这一步为参照 |
| 2 | 把纯函数搬到计算层，同时把越点走廊的默认值按载具类别放进运动律 | 必须排在第一步之后，纯函数的归属要按端口语义定。做完之后"计算层不依赖执行层"才能写成自动检查 |
| 3 | 抽取公共编排，把两个任务里镜像的连续跟随与碰撞恢复合成一份，任务包只留差异 | 依赖前两步 |
| 4 | 把 `TASK_REQUIREMENTS` 从引擎包搬到任务包 | 风险最高，会改装配期的校验逻辑，要等前三步稳定 |
