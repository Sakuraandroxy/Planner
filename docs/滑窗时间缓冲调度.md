# 滑窗连续路径调度

## 1. 目标与边界

滑窗调度负责让 AirSim 在 Qwen 后台规划期间持续飞行，并在 Qwen 返回后把新轨迹接到当前未飞完路径后面。

目标检测和任务完成由独立后台模块负责。滑窗只响应完成模块的暂停、清空和阶段切换事件，不参与判断目标是否已经到达。

连续模式的核心目标是：

- 不按固定 1、2 或 3 个点切成阻塞批次；
- 当前队列一次性交给 AirSim 非阻塞执行；
- 飞行过程中抓图并提交 Qwen；
- Qwen 返回后，在无人机到达旧路径末端前续写活动路径；
- 只有任务确认完成、发生新碰撞或轨迹确实耗尽时才停止。

## 2. 数据约定

运行时队列保存尚未飞完的绝对世界坐标点：

```text
Q = [p1, p2, ..., pn]
pi = [world_x, world_y, world_z]
```

Qwen 输入为 0-5 个 pending 增量机体坐标点，输出固定 5 个 additional 增量机体坐标点。

提交 Qwen 时会冻结以下信息：

- 抓图时无人机位置和 yaw；
- 当时发送给模型的 pending 世界坐标点；
- 对应的前视图和下视图。

即使 Qwen 推理期间部分 pending 已经飞完，新输出仍然以冻结 pending 的末端为续写起点。返回的新世界坐标点只追加到当前队列尾部，不会重新加入已经消费的点。

## 3. AirSim 活动路径

标准 AirSim 不支持向正在执行的 `moveOnPathAsync` 原地追加轨迹点。每次调用时，AirSim 会复制整条路径到服务端执行，之后修改 Python 本地列表不会改变活动路径。

因此连续续写采用重发方式：

```text
旧活动路径：A -> B -> C -> D
当前已飞过：A、B
Qwen新增：E -> F -> G

重发路径：C -> D -> E -> F -> G
```

重发只包含当前尚未飞完的旧点和新点。由于新命令前半段与旧命令剩余部分一致，并且在旧终点减速前发出，无人机可以继续沿同一方向飞行。

AirSim 参数为：

```text
drivetrain = ForwardOnly
yaw_mode = YawMode(is_rate=False)
adaptive_lookahead = 1
```

长路径的 lookahead 上限为 3m。短路径会将 lookahead 动态缩小到路径长度的一半，避免剩余路径短于固定 lookahead 时命令不启动。

## 4. 非阻塞执行

连续模式调用 `moveOnPathAsync` 后不执行 `.join()`。主循环保持运行，并按配置周期读取无人机位姿。

轨迹点在以下任一条件成立时视为已经消费：

- 无人机与轨迹点距离不超过 `PATH_REACH_TOLERANCE_M`；
- 无人机已经越过该点所在的垂直平面，且横向误差不超过 `PATH_PASS_TOLERANCE_M`。

消费点后，从世界队列和活动路径的剩余列表头部同时删除对应数量。这样 Qwen 拼接、前端显示和 AirSim 路径进度始终使用同一份“未飞完队列”。

## 5. Qwen 触发时机

默认时间缓冲为：

```text
RESERVE_TIME_S = 4.5
```

队列每段预计飞行时间为三维距离除以 `SIM.AIRSIM_VELOCITY`。

Qwen 空闲且队列不超过 5 点时，调度器在最后一个能够保留 4.5 秒的位置触发规划：

```text
当前剩余时间 >= 4.5s
飞过下一个点后的剩余时间 < 4.5s
```

此时不停止 AirSim 路径，而是在飞行过程中：

1. 记录当前位姿；
2. 抓取前视图和下视图；
3. 用当前未飞完的 0-5 个点提交 Qwen；
4. 继续执行原活动路径。

如果当前所有点总时间已经不超过 4.5 秒，则立即提交 Qwen，同时继续飞行，不再要求先执行固定一个点。

如果队列超过 5 点，则先持续飞行，直到未飞完队列降到 5 点以内，才允许提交 Qwen。

## 6. Qwen 运行期间

Qwen 运行期间不再使用固定的 `PLANNING_EXECUTE_COUNT=2` 或 3。AirSim 会继续执行活动路径中的所有剩余点，主循环每隔约 0.05 秒轮询：

- 实际飞行进度；
- Qwen Future 是否返回；
- 后台完成检测事件；
- 本次路径是否产生新碰撞。

Qwen 返回后：

1. 根据冻结 pending 末端生成 5 个新世界坐标点；
2. 将新点追加到当前未飞完队列；
3. 检测到队列尾部增长；
4. 立即重发“未飞完旧点 + 新点”；
5. 输出 `[PathStream] extend points=N`。

只要 Qwen 延迟没有超过剩余路径覆盖时间，AirSim 就不会到达旧路径末端，也不会进入等待或悬停。

## 7. 初始空队列与真正耗尽

阶段开始时队列为空，系统必须先调用一次 Qwen，因此初始启动仍然需要等待首批 5 点。

飞行过程中，如果 Qwen 延迟超过 4.5 秒并且活动路径已经全部耗尽，日志会出现：

```text
[FastSlow] active path exhausted; waiting for background Qwen
```

这是连续调度唯一正常的等待分支。若频繁出现，应增加 `RESERVE_TIME_S`，使其覆盖 Qwen 高分位延迟和抓图时间。

## 8. 完成检测与碰撞

后台完成模块可以在飞行过程中抓图和检测。

当收到 `near_stop` 或 `done_candidate` 时，运行时会：

1. 调用 `hoverAsync().join()` 停止活动路径；
2. 使用新鲜图像重新确认目标；
3. 确认完成则清空路径和队列并切换阶段；
4. 确认未完成则丢弃旧队列和旧 Qwen 结果，从当前位置重新规划。

碰撞只按 AirSim 碰撞时间戳判断本次路径新增事件。起飞或上一次飞行遗留的 `has_collided=True` 不会再触发错误后退。

## 9. 配置

```yaml
FUNCTIONS:
  FAST_SLOW:
    MAX_PENDING: 5
    RESERVE_TIME_S: 4.5
    PATH_POLL_INTERVAL_S: 0.05
    PATH_REACH_TOLERANCE_M: 0.8
    PATH_PASS_TOLERANCE_M: 1.5
    PATH_REISSUE_MIN_INTERVAL_S: 0.15

SIM:
  AIRSIM_VELOCITY: 2.0
  AIRSIM_PATH_LOOKAHEAD: 3.0
  AIRSIM_MIN_PATH_LOOKAHEAD: 0.2
  AIRSIM_ADAPTIVE_LOOKAHEAD: 1.0
```

`PLANNING_EXECUTE_COUNT` 和 `EXECUTE_COUNT` 仅保留给旧阻塞执行入口兼容，连续路径主循环不按固定点数停车。

## 10. 关键日志

首次发送路径：

```text
[PathStream] start points=5
```

实际飞过轨迹点：

```text
[PathProgress] consumed=1 queue_after=4 pose=(...) yaw=...
```

到达时间缓冲边界并提交 Qwen：

```text
[ContinuousSchedule] reason=reserve_boundary queue_time=5.30s after_next=4.10s
```

Qwen 返回并续写活动路径：

```text
[SlowPlan] appended=5 queue=7 ...
[PathStream] extend points=7
```

现场验证时应重点确认：

- 飞行期间持续出现 `PathProgress`，而不是旧的 `FastExec done`；
- Qwen 运行期间无人机仍在移动；
- 每次 `SlowPlan appended` 后紧跟一次 `PathStream extend`；
- 正常情况下不出现 `active path exhausted`；
- 阶段完成前才出现显式暂停和新鲜确认。
